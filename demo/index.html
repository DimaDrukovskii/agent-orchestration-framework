Как это работает

От входящего звонка до решённого вопроса — без участия владельца

Hermes — не скрипт с кнопками, а агент с tool-use: сам решает, что сделать на каждом шаге диалога.

01

Звонок приходит

Телефония МТС (или Twilio-адаптер на хакатоне) пересылает реплику абонента на /api/hermes/dialog.

02

Hermes ищет факты

Вызывает search_knowledge_base — не придумывает цены и инструкции, берёт их из базы бизнеса.

03

Проверяет, если нужно

Для вопросов по счёту — check_account_status, прежде чем отвечать абоненту.

04

Решает сам или переводит

Отвечает сразу, либо вызывает transfer_to_department — честно, без притворства.

Архитектура

Один агент, подключаемый проводками

Hermes спроектирован как «компьютер», к которому подводятся ключи и адреса через переменные среды — замена локального ключа на облачный Claude ничего в коде не трогает.

МТС / Twilio-вебхук→ X-API-Key→ /api/hermes/dialog→ Redis — сессия→ Claude tool-use loop→ Supabase — персист
Stateless

Любой инстанс отвечает на любой запрос

История диалога живёт в Redis по session_id, не в памяти процесса — можно поднять N реплик за балансировщиком.

Auth

X-API-Key на входе

Единый ключ на хакатон, по плану — таблица api_clients с ключом на бизнес и рейт-лимитом.

Персист

Supabase, upsert по call_id

Один call_id = один звонок = одна строка, обновляется на каждой реплике, не плодит дубликаты.

Под нагрузку МТС

Асинхронный путь обработки — скелет

POST /api/hermes/dialog/async сразу отвечает 202 и task_id, фоновый воркер обрабатывает реплику очередью — так синхронный tool-use цикл агента не держит HTTP-соединение на сотнях параллельных звонков. Интерфейс очереди спроектирован так, чтобы in-memory реализацию можно было заменить на Redis Streams/SQS без изменения вызывающего кода.
