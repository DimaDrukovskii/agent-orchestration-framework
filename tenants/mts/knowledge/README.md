# Как устроена база знаний

Это не документация проекта — это сырьё, которое читает `search_knowledge_base`
(`src/agent/tools.py`). Агент сам решает, когда сюда заглянуть, и отвечает
абоненту на основе того, что здесь написано, а не придумывает цифры.

**Механика поиска:** простой keyword-match по всем `.md`-файлам в этой папке.
Агент получает содержимое **одного** файла — того, где больше слов из вопроса
абонента совпало с текстом. Из этого прямо следует правило:

## Правило: один файл — одна тема

Не класть весь FAQ бизнеса в один файл. Если в одном файле намешаны тарифы,
доставка и возвраты — при вопросе про доставку агент может получить файл,
который на самом деле "выиграл" по тарифам, и там доставки не будет.
Дробить по темам так, как абонент сам формулирует вопрос.

## Файлы в этой папке — шаблон, не готовый контент

Эти файлы написаны **как структура**, с плейсхолдерами в `[квадратных
скобках]`. Это заготовка под любой бизнес, который подключается к Hermes, а
не реальные данные МТС — тарифы сейчас не важны (см. решение в
`docs/mts/TRACK1_PLAN.md`: демо идёт на симуляторе/сценариях, не на реальных
цифрах). Когда появится конкретный бизнес — плейсхолдеры заменяются его
данными, структура файлов остаётся.

| Файл | Тема | Что заменить |
|---|---|---|
| `company_profile.md` | Кто это, часы работы, контакты, точки присутствия | Все `[...]` |
| `services_and_pricing.md` | Какие услуги есть и как устроена оплата (без точных цифр) | Список услуг, принцип тарификации |
| `support_faq.md` | Типовые проблемы абонента и что отвечать | Конкретные сценарии под продукт бизнеса |
| `escalation_rules.md` | Когда агент сам решает звать человека (`transfer_to_department`) | Отделы, формулировки триггеров |

## Что НЕ должно жить в этой папке

- Персональные данные абонентов — это `calls`/`api_clients` в Supabase
  (`docs/website_side_bar/DATABASE_SCHEMA.md`), не markdown-файлы на диске.
- Промпт/стиль речи агента — это `src/agent/hermes_prompts.py`, не база
  знаний. Здесь только факты, которые агент *подтягивает*, а не инструкции,
  как ему *говорить*.
- Секреты и ключи — очевидно.

## Если бизнесов станет несколько (мультиарендность)

Один клиент = одна папка `tenants/<клиент>/` (эта база лежит в `tenants/mts/knowledge/`); клиент выбирается
переменной `TENANT` в `.env`. Выбор клиента по ключу доступа (`api_clients`, один сервер на много клиентов) пока не
сделан: см. `docs/mts/SCALING_PLAN.md`, этап 1.
