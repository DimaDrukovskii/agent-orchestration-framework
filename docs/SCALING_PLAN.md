# План масштабирования и встраивания в инфраструктуру МТС

Этот документ фиксирует целевую архитектуру продукта и порядок перехода к ней от
текущего состояния репозитория. Цель — не "ещё один слайд", а конкретный маршрут,
по которому МТС сможет **встроить сервис в свою инфраструктуру без переписывания
нашей стороны**: один API-контракт, один способ подключения, предсказуемое
поведение при нагрузке и отказах.

Решение по треку (`docs/TRACK1_PLAN.md`) не меняется. Этот документ — его
техническое продолжение: как дойти от хакатон-прототипа до состояния,
которое не стыдно показать как "путь в прод".

## 0. Ключевое решение: Hermes — единственный публичный агент

Сейчас в репозитории два агента с двумя контрактами:

| | `/api/dialog` (`CallOrchestrator`) | `/api/hermes/dialog` (`HermesAgent`) |
|---|---|---|
| Статус | Старый MVP, первый коммит | Целевой агент — tool use, живая речь, база знаний |
| Хранение истории | Клиент передаёт `history` в каждом запросе | Сервер хранит сам по `session_id` |
| Персист в БД | Есть (`StorageService.save_call`) | Нет — утеряно при переносе |

**Решение: публичный контракт для МТС — только `/api/hermes/dialog`.**
`/api/dialog` остаётся в коде как internal/legacy эндпоинт (на него не ссылаемся
в интеграционной документации), либо выпиливается, когда будет точно ясно, что
никто его не использует. Два параллельных контракта — это риск для интегратора:
непонятно, какой "настоящий". МТС подключается ровно к одному.

Это значит: все пробелы Hermes-агента (сессии, персист, лимиты) нужно закрыть
до того, как показывать контракт как стабильный.

## 2. Контракт для МТС — что фиксируем и не меняем без версии

Текущий формат запроса/ответа `/api/hermes/dialog` (см. `docs/HERMES_AGENT.md`)
становится **версионированным публичным контрактом**:

```
POST /api/v1/hermes/dialog
Headers:
  X-API-Key: <ключ, выданный при подключении>
  Idempotency-Key: <опционально — повтор того же запроса не создаёт дублей>

{
  "session_id": "string",
  "caller_phone": "string",
  "user_message": "string"
}
```

Правила, которые делают подключение «за 5 минут» реальностью, а не слоганом:

1. **Один API-ключ = одна настройка.** Ключ привязан к бизнесу (таблица
   `api_clients`, см. ниже), выдаётся один раз, никакой отдельной регистрации
   со стороны МТС-абонента или бизнеса не требуется — ровно то ограничение,
   что уже зафиксировано в `docs/TRACK1_PLAN.md`.
2. **Версия в пути (`/api/v1/...`), не в заголовке.** Ломающие изменения — новая
   версия пути, старая продолжает работать до отдельно согласованного срока
   устаревания. МТС не должен следить за changelog, чтобы не сломаться.
3. **Контракт ответа не меняется молча.** Поля можно добавлять, нельзя удалять
   или менять тип в рамках одной версии.
4. **Единый формат ошибки** на все 4xx/5xx:
   ```json
   { "error": { "code": "string", "message": "string", "retryable": true } }
   ```
   `retryable: true` — сторона МТС может повторить запрос с тем же
   `Idempotency-Key` без риска дублирования звонка. Это закрывает рекомендацию
   из `docs/MTS_INTEGRATION.md` ("retry один раз при временной ошибке"), но
   делает её безопасной, а не предположением.
5. **Fallback-поведение прописан явно.** Если сервис недоступен или отвечает
   `5xx` — на стороне МТС это должно по контракту трактоваться как сигнал
   «переводи на человека», а не «повтори бесконечно». Это пишем прямо в
   интеграционном доке, не оставляем на догадку интегратора.

## 3. Целевая архитектура (масштабирование)

```
                         ┌─────────────────────────┐
  МТС / Twilio-адаптер → │  Load Balancer / Ingress │
                         └─────────────┬────────────┘
                                       │
                     ┌─────────────────┼─────────────────┐
                     │                 │                 │
               ┌─────▼─────┐     ┌─────▼─────┐     ┌─────▼─────┐
               │ app instance│    │ app instance│    │ app instance│  ← stateless,
               │  (FastAPI)  │    │  (FastAPI)  │    │  (FastAPI)  │     горизонтально
               └─────┬───────┘    └─────┬───────┘    └─────┬───────┘     масштабируется
                     │                  │                  │
         ┌───────────┼──────────────────┼──────────────────┼───────────┐
         │           │                  │                  │           │
   ┌─────▼─────┐┌────▼─────┐      ┌─────▼──────┐     ┌─────▼──────┐    │
   │   Redis   ││ Claude API│      │  Supabase  │     │  Whisper   │    │
   │ (сессии,  ││  (агент)  │      │ (персист,  │     │ (STT, offline,│  │
   │  rate-lim)││           │      │  аналитика)│     │  по необходимости)│
   └───────────┘└───────────┘      └────────────┘     └────────────┘    │
                                                                         │
                                        Все внешние зависимости — за таймаутом
                                        и circuit breaker, деградация к fallback
```

Ключевой принцип: **приложение не хранит состояние локально.** Любой инстанс
может обработать любой запрос любой сессии — это условие горизонтального
масштабирования под нагрузку МТС (сотни тысяч абонентов, о которых говорит
`docs/TRACK1_PLAN.md`), и именно поэтому in-memory `_sessions` в
`hermes_routes.py` — не мелкий недочёт, а архитектурный блокер масштабирования,
который нужно закрыть раньше остальных пунктов.

### Данные

Переиспользуем уже спроектированную схему (`docs/DATABASE_SCHEMA.md`), добавляя
только то, чего реально не хватает для мультиарендности:

```sql
-- Новое: один ключ = один бизнес/подключение МТС
CREATE TABLE public.api_clients (
    id BIGSERIAL PRIMARY KEY,
    api_key_hash TEXT UNIQUE NOT NULL,   -- хранится хеш, не сырой ключ
    business_name TEXT NOT NULL,
    webhook_url TEXT,                    -- куда слать async-уведомления (см. §4.1)
    rate_limit_per_minute INT DEFAULT 100,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT NOW()
);

-- calls уже есть — добавляем только внешний ключ на клиента
ALTER TABLE public.calls ADD COLUMN client_id BIGINT REFERENCES api_clients(id);
```

Таблицы `call_feedback` и `agent_metrics` не меняются — они уже на месте,
просто должны реально заполняться из Hermes-пути (сейчас не заполняются).

### 4.1. Асинхронный путь (когда понадобится)

MVP остаётся синхронным (запрос → ответ в одном HTTP-вызове) — это осознанно,
лишняя инфраструктура очереди на этом этапе не нужна. Но контракт закладывает
путь на случай долгих операций (например, сложный tool-вызов, живой биллинг):
`webhook_url` в `api_clients` — это точка, куда можно начать слать
асинхронные уведомления (например, "звонок переведён, вот результат"), не
меняя основной синхронный контракт `/api/v1/hermes/dialog`. Не реализуем
сейчас, просто не закрываем себе дверь в схеме данных.

## 5. Тестирование — закрепляем то, что уже решено, не придумываем новое

Тестов не было — но поведение агента уже зафиксировано в двух местах:
сценарии в `docs/TRACK1_PLAN.md` ("Тестирование без живого звонка") и их
прямая реализация в `scripts/test_call.py`. Задача — не придумать новую
систему тестирования, а **оформить то, что уже работает руками, как
автоматизированный контракт.**

1. **Контрактные тесты = существующие сценарии из `scripts/test_call.py`.**
   Те же 4 сценария (штатный вопрос, сложный → перевод, экстренный перевод,
   двусмысленная фраза) становятся `pytest`-параметризацией против
   `/api/v1/hermes/dialog`, а не живым ручным прогоном. Критерий не "текст
   ответа совпал" (Claude не детерминирован), а структурный: для сценария
   "экстренный перевод" — `transfer` в ответе не `null`; для "штатного
   вопроса" — `transfer` остаётся `null` и т.д. Это прямое повторение
   уже принятой логики, не новое требование.
2. **Smoke/health тест на каждый деплой** — `GET /health`, уже есть, просто
   добавить в CI как первый шаг.
3. **Unit-тесты на `tools.py`** без обращения к Claude: `search_knowledge_base`
   с заранее известными файлами в `data/knowledge/` — проверяем, что поиск
   реально находит, не мок.
4. **`tests/test_api.py` переписывается**, а не чинится — он бьёт по
   эндпоинту, которого никогда не было в текущей архитектуре.
5. **Twilio — не тестируем вживую, по решению из `docs/TRACK1_PLAN.md`.**
   Вместо живого прозвона: тест адаптера как чистой функции — "вебхук от
   Twilio нужного формата → корректно транслируется в вызов
   `/api/v1/hermes/dialog`" на фикстурах payload'ов Twilio, без реальной
   телефонной линии. Это и есть «архитектурно грамотно, но не протестировано
   вживую» — честно по контракту функции, не по живому звонку.

## 6. Эксплуатационные требования (нужны МТС для принятия решения, не только нам)

- **Логи без PII.** Структурированный лог (`src/utils/logger.py`) не должен
  писать `caller_phone` и текст разговора в открытом виде в общий лог-поток —
  либо маскировать номер, либо писать PII только в зашифрованное хранилище
  (та же таблица `calls`, доступ к которой разграничен RLS-политикой, а не
  "allow all", как сейчас в `docs/DATABASE_SCHEMA.md` для хакатона).
- **Таймауты и деградация.** Каждый внешний вызов (Claude, Supabase, Redis)
  — с таймаутом и понятным fallback-ответом абоненту ("скажи, что переводишь
  на специалиста"), а не зависанием запроса.
- **Health/readiness раздельно.** `/health` — "процесс жив"; отдельный
  `/ready` — "Redis и Supabase доступны", чтобы балансировщик не слал трафик
  на инстанс, который не может обработать запрос полноценно.
- **Открытые вопросы комплаенса** (локализация данных, согласие на запись,
  аудит доступа) — не блокируют этот план, но явно переносятся из
  `docs/TRACK1_PLAN.md` как условие реального продакшен-подключения, не
  хакатон-демо.
