# Масштабирование и путь в продакшен

Что уже сделано, что проверено нагрузкой и что осталось до промышленного подключения. Контракт: [MTS_INTEGRATION.md](MTS_INTEGRATION.md).

## Решение по контракту

Публичный контракт один: `POST /api/hermes/dialog`. Старый `/api/dialog` и неавторизованная очередь удалены, интегратору не из чего выбирать.
Поля ответа можно добавлять, удалять или менять тип можно только с новой версией пути.

## Целевая схема

Любой экземпляр приложения обрабатывает любой запрос любой сессии, поэтому оно масштабируется горизонтально за балансировщиком:

```
МТС / телефонный адаптер → балансировщик → N экземпляров FastAPI (без состояния)
                                              ├─ Redis (сессии, лимиты)
                                              ├─ Supabase/Postgres (записи разговоров, аналитика)
                                              └─ модель, распознавание, озвучка (внешние API или свои серверы)
```

Узкое место не наш код, а лимиты внешних сервисов: число одновременных запросов к модели и озвучке и дневной лимит ключа. Для 50 живых
одновременных звонков нужно подтвердить эти лимиты у провайдера отдельно, платным прогоном по явной команде.

## До промышленного подключения

1. Ключ на клиента и ограничение запросов по нему.
2. Версионированный путь и единый формат ошибки зафиксировать как стабильные.
3. `/ready` и таймауты с понятной деградацией: при `5xx` и таймауте сторона МТС переводит звонок на человека, а не повторяет бесконечно.
4. Журналы без персональных данных: номер маскируется (`mask_phone`), текст реплик в общий журнал не пишется; хранение разговоров с разграничением доступа
   (политики RLS вместо открытого доступа, как в демо-схеме [../website_side_bar/DATABASE_SCHEMA.md](../website_side_bar/DATABASE_SCHEMA.md)).
5. Комплаенс (локализация данных, согласие на запись, аудит доступа): [PITCH_COMPLIANCE.md](PITCH_COMPLIANCE.md).
6. Телефонный канал (SIP или Twilio-совместимый поток) и живой прогон на реальной линии; сейчас проверено на тексте и на голосе в браузере.
